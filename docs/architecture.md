# Архитектура Carbon Market — подробное описание

## 1. Идея и терминология

- **УЕ (углеродная единица)** — единица учёта сокращения/поглощения выбросов
  парниковых газов, хранится и учитывается во ВНЕШНЕМ реестре (сейчас —
  заглушка `RegistryClient`, потом — реальный API национального/
  международного реестра, аналог механизмов ст. 6 Парижского соглашения).

- **Вексель (Voucher)** — САМОСТОЯТЕЛЬНЫЙ пронумерованный финансовый
  инструмент (номер вида `CM-000042`), а не просто техническая деталь одной
  сделки. Продавец **выпускает** («минтит») вексель на конкретный объём и
  характеристики УЕ из своего остатка в реестре — в этот момент объём
  замораживается (`RegistryClient.freeze_units`), и вексель существует уже
  вне зависимости от того, продан он или нет. У векселя всегда есть
  `original_seller_id` (кто выпустил) и `current_holder_id` (кто владеет
  сейчас) — это разные пользователи, если вексель успел перепродаться.

- **ГЛАВНОЕ ПРАВИЛО РЫНКА**: на продажу можно выставить только уже
  СУЩЕСТВУЮЩИЙ вексель, целиком, за ЕДИНУЮ фиксированную цену.
  «Сырые» углеродные единицы по цене за штуку продавать нельзя — этой
  возможности в API просто не существует. Вексель неделим: либо покупают
  весь его объём, либо не покупают вовсе.

- **Перепродажа / цепочка держателей**: купленный вексель можно выставить
  на продажу ещё раз (уже новым держателем, за свою цену) — это тот же
  самый пронумерованный инструмент, просто со сменившимся держателем.
  Каждый переход фиксируется в неизменяемом журнале `VoucherTransfer`
  (тип MINT → SALE → SALE → …), поэтому по номеру векселя всегда можно
  восстановить полную историю: кто выпустил, кто был промежуточными
  держателями, кто владеет сейчас — см. `GET /vouchers/number/{number}`
  (публичный эндпоинт, без авторизации — как проверка любого
  регистрационного номера).

- **Обналичивание (redeem)** — момент, когда ТЕКУЩЕМУ держателю нужны
  именно УЕ на балансе (например, для зачёта собственных выбросов), а не
  просто владение векселем. Вызывается `RegistryClient.transfer_units` со
  счёта ПЕРВОНАЧАЛЬНОГО продавца (там физически заморожены единицы с
  момента минта) на счёт текущего держателя — независимо от того, сколько
  раз вексель успел перепродаваться. После этого вексель переходит в
  `REDEEMED` и больше не может ни перепродаваться, ни обналичиваться
  повторно.

- **Объявление (Listing)** — предложение продать ОДИН конкретный вексель
  (`voucher_id`) за фиксированную цену (`fixed_price`). Больше не хранит
  ни характеристик, ни количества, ни цены за единицу — это всё
  принадлежит самому векселю.

## 2. Модель данных и её связи

```
User (физ/юр лицо)
  └── registry_account_id ──────────► CarbonUnitBatch[] (в RegistryClient)
                                            (партии УЕ с характеристиками
                                             и полями quantity/frozen_quantity)

Voucher (пронумерованный инструмент, выпускается ДО продажи)
  ├── number                         — человекочитаемый уникальный номер
  ├── original_seller_id ───────────► User (кто выпустил)
  ├── current_holder_id ────────────► User (кто владеет сейчас)
  ├── characteristics ───────────────► CarbonUnitCharacteristics
  ├── quantity                       — объём УЕ, фиксирован, неделим
  ├── registry_freeze_ref ───────────► заморозка в RegistryClient (со времён минта)
  └── status: ACTIVE -> REDEEMED

VoucherTransfer (неизменяемый журнал переходов владения — "цепочка")
  ├── voucher_id ────────────────────► Voucher
  ├── type: MINT | SALE | CANCELLATION
  ├── from_user_id (None только для MINT), to_user_id
  ├── price (только для SALE)
  └── listing_id (объявление, по которому прошла сделка)

Listing (объявление — предложение продать ОДИН конкретный вексель)
  ├── voucher_id ────────────────────► Voucher (текущий держатель которого == seller_id)
  ├── seller_id ──────────────────────► User
  ├── fixed_price                     — ЕДИНАЯ цена за вексель целиком
  └── status: ACTIVE -> SOLD | CANCELLED
```

## 3. Ценообразование

Цена всегда — единая сумма за вексель целиком (`Listing.fixed_price`).
Режимов "цена за единицу" / "комиссия за сделку" больше нет — они
принадлежали старой модели, где продавались "сырые" УЕ порциями.
`price_per_unit = fixed_price / voucher.quantity` вычисляется на лету
(в `listing_service`/`matching_service`) только для сортировки и
отображения — покупатель всегда платит `fixed_price`, не за единицу.

## 4. Жизненный цикл: от остатка в реестре до денег продавца

```
1. seller: POST /vouchers/mint {characteristics, quantity}
     → voucher_service.mint_voucher
     → замораживает quantity УЕ в реестре, создаёт Voucher(ACTIVE)
       с новым номером, пишет VoucherTransfer(MINT)

2. seller (может быть другим держателем, если вексель уже перепродавался):
   POST /listings {voucher_id, fixed_price}
     → listing_service.create_listing
     → только если seller — ТЕКУЩИЙ держатель и у векселя ещё нет
       активного объявления

3. buyer: POST /market/buy-listing {listing_id}
   (или через подбор — см. п. 5)
     → matching_service.buy_listing_direct → voucher_service.buy_listing
     → списывает fixed_price у покупателя, зачисляет продавцу,
       Voucher.current_holder_id = buyer, Listing.status = SOLD,
       пишет VoucherTransfer(SALE)

4a. buyer: POST /vouchers/{id}/redeem — обналичить (получить реальные УЕ)
4b. buyer: POST /listings {voucher_id, fixed_price} — перепродать дальше
      (тогда buyer становится seller_id в новом Listing — цепочка растёт)
```

## 5. Два сценария подбора (маршруты `/market/*`)

### Сценарий 1 — "купить сейчас, точное количество"
`POST /market/buy-exact-quantity {quantity_needed, characteristics?}`
→ `matching_service.buy_exact_quantity`. Жадно берёт САМЫЕ ДЕШЁВЫЕ (₽ за
единицу) подходящие ЦЕЛЫЕ векселя один за другим, пока суммарный объём не
достигнет требуемого. Поскольку векселя неделимы, точное совпадение не
гарантировано — либо `unmet_quantity > 0` (не набралось, тогда запрос
отклоняется `InsufficientMarketSupplyError` — превью через
`/market/quote/...` показывает это ДО оплаты), либо последний вексель
может немного "перекрыть" запрошенный объём.

### Сценарий 2 — "инвестор, есть сумма денег"
`POST /market/invest-amount {budget_amount, characteristics?}`
→ `matching_service.invest_amount`. Идёт по тем же отсортированным по
цене векселям и берёт целиком каждый, который укладывается в остаток
бюджета (не обязательно подряд — если очередной вексель не влезает,
пробует следующий).

### Прямая покупка (ручной выбор на витрине)
`GET /listings?...&sort_by=price|quantity|created_at` — покупатель сам
смотрит и сортирует объявления (`listing_service.browse_listings`), затем
`POST /market/buy-listing {listing_id}` — покупает конкретный вексель
целиком, без алгоритма подбора.

Все пути в итоге вызывают `voucher_service.buy_listing` — бизнес-инвариант
покупки (деньги + смена держателя + запись в журнал) не дублируется.

## 6. Алгоритм подбора (matching_service) — ограничения и развитие

Реализован **жадный** алгоритм по неделимым предложениям (сортировка по
цене за единицу + последовательный whole-item выбор). Это быстро и
просто, но НЕ гарантирует глобально оптимальную комбинацию — это, по
сути, задача о рюкзаке.

**Точка расширения**: заменить `_allocate` на точный солвер (ILP через
`pulp`/`ortools`) с той же сигнатурой, не трогая остальной код — сервисы
уже изолируют этот алгоритм от API-слоя и от репозиториев.

## 7. Продавец: сколько он может заминтить (`seller_capacity_service`)

```
доступно_для_выпуска_векселя =
    остаток_в_реестре(характеристики)   # RegistryClient.get_balance(...).available_quantity
```

Упрощение по сравнению со старой моделью: минт СРАЗУ замораживает объём в
реестре (в отличие от старого Listing, который лишь виртуально
резервировал объём до фактической покупки), поэтому вычитать "уже
выставленное в других объявлениях" больше не нужно — `available_quantity`
из реестра уже полностью учитывает всё, что было заминчено ранее.

## 8. Аутентификация (заглушка)

`core/security.py` — простой opaque-токен в `dict` с TTL,
`core/dependencies.py` — `get_current_user` через заголовок
`Authorization: Bearer <token>`. Интерфейс (`create_token`/
`get_user_id_by_token`/`revoke_token`) намеренно такой же, какой будет и
при переходе на JWT — переписывать вызывающий код не придётся.

## 9. Интеграция с реальным реестром УЕ

Единственная точка интеграции — `services/registry_client.py`. Публичный
интерфейс (`get_balance`, `freeze_units`, `unfreeze_units`,
`transfer_units`) не изменился при переходе на вексельно-центричную
модель и спроектирован так, как должен выглядеть и с реальным
HTTP-клиентом к API реестра. Замена реализации не потребует изменений в
`matching_service`, `voucher_service`, `seller_capacity_service` — они
используют только интерфейс, не детали.

## 10. Точки расширения (не входят в MVP, но заложены в модели)

- **Оптимальный подбор предложений**: см. п. 6.
- **Частичная отмена/rollback при сбое посреди сборки покупки** (сценарии
  1/2): если один из выбранных `Listing` "утёк" между расчётом quote и
  фактической покупкой (кто-то опередил), уже купленные в рамках этого же
  запроса векселя сейчас не откатываются автоматически — нужна
  транзакционность на уровне `matching_service._execute`.
- **Отмена покупки только для последнего перехода**: `cancel_purchase`
  откатывает исключительно САМУЮ ПОСЛЕДНЮЮ покупку (пока вексель не
  перепродали дальше и не обналичили) — более ранние держатели цепочки
  такой возможности не имеют, это осознанное ограничение MVP.
- **Персистентность**: все `repositories/*_repo.py` сейчас — тонкая
  обёртка над `InMemoryStore`; переход на Postgres/SQLAlchemy — замена
  реализации репозиториев без изменения сервисов и роутов.
- **KYC/верификация юр. и физ. лиц** перед допуском к торгам — сейчас
  регистрация ничего не проверяет, кроме уникальности email.
